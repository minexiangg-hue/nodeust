# NODE 第一轮内测计划

版本日期：2026-09-09。本文是待执行计划，不代表内测已经开展。

## 目标与规模

第一轮重点验证：用户能否理解并完成“发布需求 → 找到合适对象 → 匿名聊天 → 双方同意交换联系方式 → 关闭需求”，以及权限、数据保存和手机体验是否可靠。

建议首批 8–12 名受邀用户，持续 3 天；另设 1 名 Owner 负责反馈分级和日常检查。至少覆盖 iPhone Safari、Android Chrome 和桌面浏览器；用户包含有换宿、物品交换和学习互助需求的人。先完成下述启动条件，再发送邀请。

本轮不以大量拉新、真实成交数或高并发承载能力为验收目标。受邀测试任务与自然产生的真实需求分开记录，避免把任务完成当作市场需求证据。

## 启动条件：当前必须处理的事项

1. **登录身份验证。** 当前独立预览网关仅输入已注册用户名即可登录，未验证密码、验证码或 HKUST SSO。知道用户名的人可能进入他人账号，包括 Owner；应用内角色权限不能弥补这一缺口。正式邀请前必须增加能验证账号持有者的登录机制，且不能只用“隐藏网址”或一个共用邀请码代替。明确告知测试用户当前是否已经接入 HKUST 身份验证。
2. **受控预演。** 登录机制修好之前，仅限开发者组织 2–3 个测试身份演练，不收集真实联系方式、真实聊天内容或其他敏感资料，不对外传播测试入口。
3. **备份与恢复。** 邀请前备份 MySQL，并备份当前网关的账号文件及运行配置；限制备份访问权限。确认上一版构建可恢复、数据库健康检查可用。现有维护模式只替换首页，不阻止已打开页面继续调用接口；涉及停写时需要额外安排。
4. **准备任务与记录。** 建立测试者代号、设备、任务完成情况和反馈表，登记开始时的统计页读数。手工测试账号仍会计入统计，单独登记扣除，不能据此直接声称有多少真实用户。

## 主要验证内容

| 目标 | 测试动作 | 观察和验收重点 |
|---|---|---|
| 新用户能看懂 | 不先讲解，让用户登录后找发布入口、理解地点标签 | 能说清 NODE 的用途、地点是手选标签；记录卡住的位置 |
| 需求发布与发现 | 发布住房、交换、学习和其他需求；切换地图／列表，搜索和筛选 | 新帖在另一设备可见；表单失败有提示；不会误发重复帖子 |
| 匹配有效 | A 发布 Hall VII → Hall III，B 发布反向需求，再试非互补路线 | 双向路线进入匹配；无关路线不出现。当前为精确文本比较，不支持模糊匹配或多方换宿 |
| 匿名会话可靠 | 从需求发起会话，双方回复，刷新、退出重登后继续 | 消息归属正确、保存完整；重复打开同一帖子不重复创建会话 |
| 联系方式经同意交换 | 用虚构联系方式，先单方申请，再由对方同意 | 单方申请不公开联系方式；双方同意后双方均可见；失败能正确提示 |
| 发帖人能管理需求 | 查看自己的帖子，关闭、重开、删除 | 关闭后退出广场；删除后不可重开；已有会话保留；不能操作他人帖子 |
| 权限和处置有效 | 用受控身份举报帖子、处理举报；普通账号尝试访问 /owner/stats | 普通账号看不到统计或管理数据；移除内容不再公开；处置日志保留 |
| 手机使用顺畅 | 小屏幕完成发布、阅读、聊天、资料编辑；切换三种语言 | 键盘不挡发送按钮；弹窗可滚动和关闭；文字不被截断；入口容易找到 |
| 服务异常可理解 | 在测试设备暂时断网后操作，再恢复网络 | 失败不能误报成功；恢复后内容一致。避免对正式服务主动制造故障 |

范围说明：当前主界面“Save draft”按钮没有实现；正式邀请前应隐藏、禁用并说明，或完成实现。聊天“Online”是静态文案，不能作为在线状态；应调整说明。公开 feed 最多加载 100 条，匹配和收藏展示依赖这一批数据，不能用本轮小样本证明大规模数据下完整可用。

## 三天安排

| 阶段 | 安排 | 产出 |
|---|---|---|
| D0：邀请前 | 完成登录验证与备份，进行双账号预演，处理会阻断测试的已知问题 | 启动检查记录、版本标记、初始账号统计 |
| D1：引导测试 | 8–12 人分成两人一组，每组 20–30 分钟，先独立摸索，再完成核心任务 | 每一步成功／失败、耗时、是否需要帮助、设备信息 |
| D2：自然使用 | 允许用户自行发布非敏感需求；每天集中查看两次反馈 | 用户自发行为与问题记录，区别于指定任务 |
| D3：回访与复测 | 每人约 10 分钟，复测修复项并整理共同问题 | 内测结论、下一轮优先级、是否扩大邀请范围 |

回访问四个问题：你觉得 NODE 解决什么问题？哪一步最困惑？什么情况下会再回来？与目前使用的群聊或其他方式相比，哪里更方便、哪里更麻烦？不预设用户一定愿意继续使用。

## 记录方式与衡量指标

现有隐藏页 `/owner/stats` 仅 Owner 可访问，显示已建立 NODE 资料的账号数、今日／近 7 天／近 30 天新增、账号状态和 30 天趋势。它不统计 PV、UV、在线人数、日活或留存，也不覆盖只在网关注册而未建立 NODE 资料的账号。

第一轮先用人工任务表补齐行为数据，不为本轮引入全站埋点或新数据表：

- 邀请人数、实际进入人数、完成核心流程人数，均报告实际分子／分母。
- 关键任务独立成功率：成功次数 / 尝试次数，区分有无他人帮助。建议每条关键流程至少完成 10 次尝试，目标 ≥90%；小样本仅用于发现问题。
- 首次独立发布耗时：目标多数人 5 分钟内完成；另记录最慢案例和原因。
- 第二天主动回访人数：通过自愿回访和测试记录确认，与被提醒回来的用户分开，不用“账号 updatedAt”推算活跃。
- 问题数按严重程度分类，记录修复后是否由原报告人确认。
- 所有真实隐私泄露、越权和数据丢失问题要求为 0 个未解决项。

反馈优先从现有意见箱提交；每条附：测试者代号、设备／浏览器、发生时间、操作步骤、预期结果、实际结果。截图应遮住私人信息，不提交密码、验证码或真实联系方式。紧急问题使用事先约定的负责人联系渠道，不能只依赖意见箱。

## 问题分级与处理

| 级别 | 例子 | 处理方式 |
|---|---|---|
| P0 | 冒用账号、越权读取、未同意公开联系方式、数据丢失 | 立即暂停扩大测试，通知负责人，必要时停用相关功能；完成修复和权限复测再恢复 |
| P1 | 无法登录、发布或聊天；高频重复数据；主要手机无法操作 | 当天优先排查；受影响流程修好后再继续测试，不预承诺修复时长 |
| P2 | 排版、文字、入口难找、非阻断性体验问题 | 归类后批量修复，避免频繁打断用户测试 |

修复后先在隔离环境验证，再安排短暂部署窗口。涉及数据库变更时另做备份与迁移方案，不能只靠回退构建恢复数据。

## 第一轮结束时的决策

可扩大下一轮的建议条件：登录验证已落实；核心流程至少 10 次尝试且独立成功率 ≥90%；无未解决 P0/P1；三类主要设备完成复测；有明确的用户需求反馈与负责人可承担下一轮处理量。

未达标就继续小范围修复与复测，避免用账号增长掩盖流程故障。最终形成一页结论：参与人数与设备、流程完成情况、主要阻碍、已修复问题、剩余风险、下一轮最多三项优先任务。
